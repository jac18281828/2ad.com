Infinite Maze is a pixel-art platformer in which you climb, by torchlight,
through an Egyptian tomb that goes on forever in every direction.

Ever since I was little I have wanted to make a game with infinite
playability. I call it Infinite Maze.

The world is static, because the generator derives every room from a SHA3 hash
of the seed and the room's position. The same seed always builds the same
world, so every room is infinitely interconnected and consistent through
hashing, and every entry in the maze connects to every other entry with
probability 1.

## Climbing by torchlight

You play an explorer in a fedora who runs along corridors, climbs ladders,
walks stone stairs and jumps. The rooms are dark blue chambers carved
with hieroglyphs, and the torch lights only a circle around you, so most of
the tomb sits in shadow until you reach it.

The torch is our clock. A full torch burns for 300 seconds, and its light
shrinks as it burns, to a quarter of its reach in the last tenth. A
turquoise brazier relights it to full. An oil jar in a dead end adds 60
seconds. When the burn reaches zero the torch gutters to an ember for 10
seconds, and the run ends unless you reach a flame in that time.

![A sandstone wall fills the screen, lit gold by the torch, with a single narrow chamber cut into it. The explorer stands on a ledge beside a brass brazier burning with a turquoise flame, and a wooden ladder drops from the ledge into a dark shaft below.]({static}/images/2026/maze-brazier.png)

A brazier is your lifeline, along with the oil jars you can use to boost your
torch. The generator spaces braziers so that enough flame is available to solve
each room, but success is not certain.

The generator places hints for a lost explorer, and more of them appear as the
torch burns down. At some junctions a carved arrow high in the room points along
the way on, and about once a tomb a skeleton slumped in a lower corner points
the same way with its arm. When the torch falls below half, a second set of
skeletons fades in, so the hints thicken when you can least afford a wrong turn.
Dust is a hint too. In some dead ends, more often the long ones, it drifts back
toward the way you came in, and on the way on it hangs still, so moving dust
means turn around.

The music is synthesized in the browser, a Middle Eastern scale over a frame
drum. As the torch dims the synthesizer adds layers and quickens the beat, so
you hear the torch running low before you see it.

The score counts the tombs you solve along your way on, and you solve a tomb by
leaving it through its exit door. Every 100 tombs earn a rank, and what the
ranks are is yours to find out over a lifetime of solving.

Coins lie in dead ends and in rows of three along corridors, and you collect
each one as you pick it up. Coins lure you into dead ends, but the torch is
always burning.

## Phone, controller or keyboard

Accessibility is the key to a great experience, so the game runs in the
browser and plays on whatever you have in your hand. A link is all a friend
needs to start climbing.

The controls are forgiving. Up or down takes the ladder or stair in the cell you
stand in from anywhere on its floor, so a thumb on glass is precise enough to
climb. A save code carries your place in the maze between devices, so a climb
started on a laptop at lunch carries on from the phone on the way home.

The touch controls and the gamepad both send the keyboard's own key events, so
the game has one set of key handlers and every input method plays the same
game.

## Save codes

You pick one of four difficulties on the title screen, and each sets how many
rooms a tomb holds: 2×2 at EASY, 3×3 at MEDIUM, 4×4 at HARD and 6×4 at ULTIMATE.
The tombs and the doors between them are the same at every level, and only the
rooms inside a tomb differ.

A save is the seed code and one integer, such as `K7Q2-M9XA:4813`. The integer
packs the signed coordinates of a room into one number:

```
z(n) = 2n for n ≥ 0, else −2n − 1
a = z(x), b = z(y)
p = a ≥ b ? a² + a + b : a + b²
```

The first line folds the signed integers onto the naturals, and the last packs
the pair into one number. To resume, the decoder inverts the pairing and the
generator rebuilds that room straight from the hash, so no earlier room needs
replaying. Since every room is a pure function of the seed and its position,
you can type the code on another device and resume in the same room.

![The pause screen over a dimmed tomb. P pauses and shows the map of the passages you have walked, with the save
code under it, and C copies the code. The game also keeps your last save, its
run and your coins in local storage, so after a reload CONTINUE? picks up
where you stopped.

A save code holds coordinates below 2²⁵ rooms in each direction. A room takes
six seconds to run across, so walking that far sideways would take about six
years of running, assuming the maze ever ran in a straight line, which it does
not.

## A world defined by static rules

A seed code is 8 Crockford base32 characters, 40 bits in all, and the
generator hashes it into a world key. Every random value in the game then
comes from one hash of that key, a tag and some coordinates:

```
WORLD = SHA3-256("infinite-maze/v1" ‖ code)
H(tag, n₁, n₂, …) = SHA3-256(WORLD ‖ tag ‖ int64be(n₁) ‖ int64be(n₂) ‖ …)
```

The integers use a fixed width, so `(1, 23)` and `(12, 3)` hash as different
inputs. Since every value comes from a fresh hash of its own tag and
coordinates, each value stands alone, and the stream repeats only on a SHA3-256
collision. This is also why the world is static. The generator builds each room
from the hash alone, so it can build any room in any order, a million tombs up
included, and get the same answer.

The game carries its own SHA3-256, a compact Keccak-f[1600] checked against
the FIPS 202 test vectors. Bulk randomness inside a room comes from sfc32,
seeded from the first 16 bytes of a digest. Generation uses integer arithmetic
only, so a seed builds the same world on every JavaScript engine.

The world has two scales, and both use the same rule, a tree that joins all the
doors. A board is one room, a 12×7 grid of cells, a little larger than two
screens in each direction. A tomb is a grid of boards, and tombs tile an
unbounded plane.

Inside a board, the generator grows a spanning tree over the 84 cells with the
growing-tree algorithm. It extends the newest cell 60% of the time and a
random one otherwise, and it weights horizontal links 4 to 1 over vertical and
diagonal ones. A horizontal link becomes a corridor, a vertical one a ladder
and a diagonal one a stone stair. The generator then carves the tree down to
40 to 50 cells by level and leaves the rest as rock.

The game builds boards lazily. It holds the tombs within one tomb of the
explorer in each direction and builds each board as that board comes within
one board of the camera, in 0.7 ms on average.

## Room continuity

Each tomb has one exit door, up, left or right, so following exits from tomb to
tomb only climbs or moves sideways. The wall between two side neighbours points
one way, so a sideways step crosses it in only one direction. A hash of the
tomb's position picks among the open directions. A tomb holds an entry door
wherever a neighbour's exit opens into it, so it has one exit and up to three
entries.

Inside a tomb the boards form a tree that joins all its doors: a trunk from an
entry to the exit, tributaries from the other entries and dead-end branches,
and every other board position is rock. Inside a board the cells form a tree
that joins all of that board's doors.

Doors match across every seam because both boards on a shared wall read the
same hash for the door's position. Neither board reads from the other, so the
generator can build them in either order, or hours apart, and the doors still
line up.

## One tree, pretty much for sure

Every corridor in Infinite Maze belongs to one tree, and that tree has no end.
That is a strong claim about an infinite object, and only a finite piece of it
can ever be checked, so it is worth saying which parts rest on construction,
which on probability and which on tests.

### Certain, whatever the hash says

The maze is trees nested inside trees. The cells of a room form a tree, rooms
join through single doors into a tree for each tomb, and tombs join through
their exit doors. A tree has exactly one path between any two of its points, so
wherever you stand there is exactly one way to anywhere else, and every dead
end you walk into is a branch of that one way.

Suppose a loop of tombs existed. To close, it would have to come back down or
circle within a row. Exits only climb or move sideways, so it can't come back
down. Within a row the sideways exits are one-way steps along a line, and a
line of one-way steps has no way back to where it started. So the loop can't
exist.

These rules hold for every value the hash can return, because the hash only
chooses among moves the rules allow. A broken hash could make a dull maze, but
it would still be a maze with no loops, doors that line up on both sides of
every wall and one path between any two cells.

### Almost sure, if the hash flips fair coins

The way up leans on the hash behaving like fair coin flips. A walk from tomb to
tomb climbs whenever its tomb exits up, and otherwise steps sideways. A sideways
step happens about half the time, so a walk that runs 100 tombs sideways before
it climbs has odds near one in 2<sup>100</sup>, and a walk that never climbs has
probability 0.

The joins also rest on the hash behaving like fair coin flips, since two tombs
share a tree only when their walks upward merge. Follow two walks up from tombs
side by side. In each row each walk can drift left or right before it climbs, so
the gap between them wanders like a drunkard on a line. George Pólya proved in
1921 that a random walk on a line or a plane returns to its start with
probability 1, and that in three dimensions it may wander off for good. Shizuo
Kakutani put it as "a drunk man will find his way home, but a drunk bird may get
lost forever." The gap between two walks is a drunk man. It closes, the walks
merge, and from there they climb together, so every tomb joins the one tree.

Pólya's theorem has a sting in it. The expected time to come home is
infinite, so a meeting can come absurdly late. On seed 0000-0000 the walks from
tombs (0, 0) and (10, −50) are 15 columns apart at row 0 and first meet at row
773,851. At a tomb a minute, climbing that far takes a year and a half without
sleep, for two tombs that started a few screens apart.

For any one seed the hash has already fixed every wall, so two walks either
meet or they don't, and the answer was settled before anyone looked. The
probability lives in the fair-coin model, and in that model the walks that
never meet have probability 0, the way an endless run of tails has probability
0 for a fair coin, something you can write down and should never expect to
see. Mathematicians call that almost surely.

### SHA3 is not a coin

SHA3-256 is a real function, so it is fair to ask how far it can stray from fair
coins. It has 2<sup>256</sup> outputs. Two given inputs collide with probability
2<sup>−256</sup>, and over a lifetime of play, a trillion hashes or so, the
chance of even one collision is near 2<sup>−177</sup>. A collision would change
nothing you could see, since the no-loop rules hold for every value the hash
returns.

Odds like 2<sup>−177</sup> and 2<sup>−100</sup> are past the point where
probability means anything. Nothing in a lifetime, or in the age of the
universe, is rare enough to compare them with, and expecting one to happen is
irrational.

### Every room has a twin

A room is built from a finite number of choices, so the generator can build
only finitely many rooms. The maze holds infinitely many, so by the pigeonhole
principle some room has to repeat, and that holds for any hash at all. In the
fair-coin model the claim gets stronger. Rooms far apart read independent
hashes, so every room the generator can build turns up again, almost surely,
and infinitely many times over. So does every tomb, and every neighbourhood of
tombs around it.

The number of possible rooms is finite, and it is too many to count, too many to
play, too many to remember, but fun to think about. A lifetime of play, a room
every six seconds for eight hours a day over fifty years, reaches about 90
million rooms. There are so many versions of every room that many lifetimes of
play would be required to discover a twin. The twins exist, infinitely many of
them, and the twin of the room you stand in sits unreachably far away, opens
onto different neighbours and changes nothing about the one tree. Then we have a
good challenge here. Find a room and its twin.

### What the tests check

Construction covers the shape and probability covers the way up and the joins,
so the tests check that the code builds what the argument assumes. A harness
runs the generator from the same source the game uses, over 2,121 tombs, columns
−10 to 10 by rows −50 to 50, at each of the four difficulties.

It checks SHA3-256 against the FIPS 202 vectors, so the hash is the real one.
It rebuilds every connection from the doors on both sides of each wall, so it
tests the seams, the trees and the exit rules without trusting the generator's
own bookkeeping. It follows every exit walk out of the window within 100,000
steps, then climbs from tomb (0, −50) to row 50 and searches cell by cell to
the exit door at the top. Last, a fixed seed has to produce a fixed digest, so
the world built today is the world built tomorrow.

This is not a machine-checked proof. The construction argument is written out
by hand in the specification, the joins rest on a model of the hash, and the
tests cover a finite window of an infinite plane. That proof would make a good
paper.

## One file

For all that, the game is small. It ships as one self-contained HTML file, since
the music is synthesized and the sprites live in the source as palette strings.
The source itself is modular, a pure generator in one set of ES modules and the
game in another, and a small build script bundles them into the file the site
serves.
